# contract-diff

`python diff.py <v1> <v2> out/<이름>` 이 바뀐 곳을 덩어리(H1, H2 …)로 나눠 `out/<이름>/diff.json` 에 쓴다 → 너는 그걸 읽고 `out/<이름>/summary.json` 을 쓴다 → `python check.py <v1> <v2> out/<이름>` 이 원문과 대조하고 `out/<이름>/변경점.md` 를 만든다.
너는 **분류하고 설명만** 한다. 어디가 바뀌었는지는 diff.py 가, 인용이 진짜인지는 check.py 가 본다.

## 순서

1. 두 파일 경로와 결과 이름을 정한다(이름이 없으면 파일 이름에서). `python diff.py <v1> <v2> out/<이름>` 을 돌린다.
2. `out/<이름>/diff.json` 을 Read 로 읽는다. `hunks` 가 바뀐 곳 전부, `text_new` 는 새 버전 전문(누가 갑·을인지 등 맥락), `renumbered` 는 내용 그대로 번호만 바뀐 조항이다.
3. hunk 를 **하나도 빼지 않고** 둘 중 하나로 나눈다.
   - **변경 항목**(`items`): 권리·의무·금액·기간·범위·책임·조건이 하나라도 달라진 것. 조항 추가·삭제는 항상 여기.
   - **표현만 바뀜**(`wording_only`): 뜻이 그대로인 말투·어순·띄어쓰기 변경만.
   - 헷갈리면 변경 항목으로 쓴다. 표현 정리처럼 보여도 같은 문장 안에 숫자·조건이 바뀌었으면 변경 항목이다.
4. `summary.json` 을 쓰고 `python check.py <v1> <v2> out/<이름>` 을 돌린다.
5. `✗` 가 나오면 summary.json 을 고치고 4로. **오류가 0건이 될 때까지 끝내지 않는다.**
6. 사용자에게 `변경점.md` 경로, 위험도 높음 항목, 미검토가 있으면 그 건수를 짧게 알린다.

- `diff.py`·`check.py`·`test_check.py`·`verify.py` 와 입력 계약서는 **절대 고치지 않는다.** 검사기가 틀렸다고 보이면 멈추고 어떤 입력에서 왜 그런지 보고한다.
- `out/<이름>/` 밖에는 쓰지 않는다.

## 쓰는 규칙

- **인용(`before`·`after`)은 hunk 의 `old`·`new` 에서 이어진 한 구간을 글자 그대로 복사한다.** 줄임표(…)·생략·두 문단 이어 붙이기·말 바꾸기 금지. 바뀐 글자가 들어간 구간이어야 한다.
- 숫자가 바뀐 hunk(`numbers_old_only`·`numbers_new_only` 가 비어 있지 않음)는 그 숫자가 들어간 문장을 인용한다. 표현만 바뀜에 넣지 않는다.
- 조항 추가는 `before: null`, 삭제는 `after: null`.
- **요약 문장(`summary`)의 숫자는 인용에 있는 숫자만 쓴다.** "2배", "3개월 줄었다"처럼 계산한 숫자를 쓰지 않는다(조 번호 `제5조` 는 괜찮다).
- 요약은 법률 용어 대신 쉬운 말 한두 문장: 무엇이 어떻게 바뀌었고 우리 쪽에 무슨 뜻인지. 우리 쪽은 요청에 적힌 회사, 없으면 양쪽 입장을 같이 쓴다.
- `risk` 는 `높음`(돈·책임·권리가 우리에게 불리하게 크게 바뀜) / `중간`(조건·기한·범위가 바뀜, 확인 필요) / `낮음`(정의·절차처럼 영향이 작음).
- 같은 이유로 묶이는 hunk 는 한 항목에 여러 개 넣어도 된다. 한 hunk 를 변경 항목과 표현만 바뀜 양쪽에 넣지 않는다.

## 스키마

값은 형식 설명용 예시다.

```json
{
  "items": [
    {"hunks": ["H1"], "risk": "중간", "summary": "쉬운 말 한두 문장",
     "before": "옛 글에서 그대로 복사한 구간", "after": "새 글에서 그대로 복사한 구간"}
  ],
  "wording_only": [
    {"hunk": "H2", "why": "~하여야 → ~해야, 뜻 같음"}
  ]
}
```

어디에도 안 넣은 hunk 는 오류가 아니라 보고서 맨 위 `미검토` 로 올라간다. 일부러 남기지 말고, 판단이 안 서면 변경 항목에 `중간` 으로 넣는다.
